# 设计文档 — 系统设置后端与集成方案（M2/M3/M4）

> 配套 PRD：`docs/PRD-系统设置与主题中心.md`  
> 目标：把前端已落地的「系统设置四件套 + 主题系统」从「UI 占位 / localStorage 预览」接入真实后端，使品牌持久化、邮件可用、第三方登录跑通。

## 1. 总体架构

```

│ Express Server (server/)                                     │
│  /api/admin  (rbac.js)  ── requirePermission('system:config') │

│  /api/auth   (auth.js)   ── 新增「第三方登录」入口             │
```

## 2. 数据模型

### 2.1 新增 `system_settings`（单行业务配置行）

```sql
-- 005_system_settings.sql
CREATE TABLE IF NOT EXISTS system_settings (
  id            INTEGER PRIMARY KEY DEFAULT 1,   -- 单租户固定一行
  brand         JSONB NOT NULL DEFAULT '{}'::jsonb,
  email         JSONB NOT NULL DEFAULT '{}'::jsonb,
  appearance    JSONB NOT NULL DEFAULT '{}'::jsonb,
  updated_by    INTEGER REFERENCES portal_users(id),
  updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
INSERT INTO system_settings (id) VALUES (1) ON CONFLICT DO NOTHING;
```

- `brand`: `{ name, shortName, welcome, description, logo, footer }`
- `email`: `{ enabled, host, port, encryption, from, fromName, username, passwordEnc }`（密码仅存密文）
- `appearance`: `{ defaultMode, defaultAccent, defaultCollapsed }` —— 作为**新用户/未登录**的默认值；已登录用户的个人偏好仍优先读 localStorage。

### 2.2 复用既有表

- `oauth_providers(provider, name, enabled, config JSONB, sort_order)` —— `config` 存 `{ corpId, agentId, secretEnc, ... }` 等。
- `user_identities(user_id, provider, external_id, profile)` —— 登录绑定关系。

> 两套数据库（pg / sqlite）都需补 `005_system_settings.sql`，参考 `migrations/pg|sqlite/004_oauth_providers.sql` 的现有写法。

### 3.0 公开：品牌信息（新增，原设计未列）
```
GET  /api/brand
  → 200 { name, shortName, welcome, description, logo, footer }
  → 公开（无需登录）：登录页在未登录状态下也要能渲染系统名 / Logo
  → 只返回 brand 段，天然不含 email / oauth 密文
```
> 设计补充：品牌若只有鉴权接口，登录页（无 token）拿不到，改名就只能在登录后生效 —— 与 PRD「改完立刻在登录页看到」矛盾。故拆出公开只读端点。

### 3.1 设置读写（挂 `/api/admin`，复用 `rbac.js` 的 `requirePermission`）

```
GET  /api/admin/settings
  → 200 { brand, email, appearance, oauth: [ {provider,name,enabled,config,masked} ] }
  → 鉴权: system:config
  → 注意: email.password / oauth secret 不返回明文，返回 masked=true 占位

PUT  /api/admin/settings
  body { brand?, email?, appearance? }
  → 校验 brand.name 非空；email 字段若提供则加密密码后写入
  → 200 { ok:true, updated_at }
  → 鉴权: system:config
```

### 3.2 邮件测试（M3）

```
POST /api/admin/settings/email/test
  body { to }
  → 用当前 system_settings.email 配置发一封测试信
  → 成功 200 { ok:true, delivered:true }；配置不全/连接失败 422 { error, detail }
  → 鉴权: system:config
```

- 建议服务端用 `nodemailer`，SMTP 密码从 `email.passwordEnc` 解密后使用。

### 3.3 第三方登录（M4）

```
GET  /api/oauth/:provider/authorize
  → 302 跳转到厂商授权页（企微/钉钉/飞书），state 含抗 CSRF 随机串 + 回跳路径
  → 公开（登录页调用）

GET  /api/oauth/:provider/callback?code=&state=
  → 用 oauth_providers.config 换 token → 取 external_id/profile
  → 查 user_identities：
      命中 → 直接登录并下发会话
      未命中 → 进入「首次登录绑定」：若已登录则绑定当前账号；否则引导注册/绑定
  → 完成 302 跳回后台或登录后首页
  → 公开
```

## 4. 密钥管理（必须）

- 邮件密码、OAuth Secret 一律 **AES-256-GCM** 加密后落库（`passwordEnc` / `config.secretEnc`），密钥取自环境变量 `SETTINGS_ENC_KEY`（32 字节）。
- `GET /settings` 返回时对这些字段只回 `masked: true`，绝不下发明文。
- 前端 `SettingsView` 的密码框为 `type=password` 且值为空占位（用户改了才传，不改不覆盖）。

## 9. 实现踩坑记录（M2 实测）

1. **`ON CONFLICT` 里重复写 `$1..$4` 会直接打挂服务。**
   sqlite 侧 `translateForSqlite` 把每个 `$n` 逐个展开成 `?`，`VALUES` 与 `DO UPDATE` 各写一遍就变成 8 个 `?` 却只传 4 个参数 →
   `RangeError: Too few parameter values were provided`，且因为没人 catch，unhandled rejection 让 **node 进程直接退出**。
   **修法**：`DO UPDATE SET col = excluded.col`（pg / sqlite 都支持），占位符只出现一次；同时给 handler 套 `wrap()` 兜底转 500。

2. **JSON 列在 pg 也用 TEXT，不用 JSONB。**
   为了让两套方言共用同一条 SQL（不必写 `::jsonb` 这种 sqlite 不认识的转换），序列化差异统一由 `lib/settings.js` 的 `parseJson` 屏蔽。单行配置表没有索引需求，代价可忽略。

3. **验证脚本要用 node，不要用 curl。**
   Git Bash 走 GBK 代码页，中文经 shell 传参会被吃掉（写成 `?` 或乱码），看起来像「存坏了」。用 node 原生 `fetch` 发真 UTF-8 才能验证中文往返正确。

4. **段隔离写入**：PUT 只更新本次传来的段（`brand` / `email` / `appearance`），未传的段保持原值，避免「只改品牌把邮件配置冲掉」。已由断言覆盖。

5. **前端表单回填时机**：`form` 在 setup 期拷贝值，而服务端品牌是异步加载的，可能晚于 setup → 设置页加 `onMounted` 用 `brand` 回填表单，否则打开设置页看到的是默认值。

## 10. 资源组管理界面（M5，已完成）

### 10.1 背景
迁移 003 就建好了资源组三张表、后端 5 个 `group:*` 接口也齐了，但前端一直是 `soon: true` 占位菜单 —— 意味着**只能靠 curl 操作白名单授权**，管理界面缺失。

### 10.2 后端补口
| 接口 | 变更 | 原因 |
| --- | --- | --- |
| `GET /api/admin/groups/:id` | **新增** | 原列表只返回 `member_count` / `resource_count`，无法还原勾选态，UI 无从回显 |
| `PUT /groups/:id/items`、`/members` | 加组存在性校验 | 原来往不存在的组写也返回 `ok:true` |
| `DELETE /groups/:id` | 返回 404（组不存在） | 原实现无论删没删都 200 |
| 全部 group 路由 | 套 `wrap()` | 同 §9.1，避免 DB 异常打挂进程 |

### 10.3 前端
- `views/admin/GroupsView.vue`：左列表 + 右详情（资源 / 成员两个 Tab），风格对齐 RolesView
- 资源池来自 `GET /api/resources`（超管取全量），类型名来自 `GET /api/resource-types`；成员来自 `GET /api/admin/users`
- 界面上明确标注「资源类型由 `server/resource-types.setup.js` 注册，当前为脚手架示例」，避免把示例数据当成真实业务
- 新建组后**自动选中**该组，省掉「建完还得再点一次」

### 10.4 新增踩坑
6. **SQLite 默认关闭外键，级联删除是假的。**
   `db.js` 只设了 `journal_mode` / `busy_timeout`，没开 `foreign_keys` → schema 里写的 `ON DELETE CASCADE` 全部失效，删资源组会留下 `resource_group_items` / `members` 孤儿行；更糟的是孤儿行仍能被「用户←成员←组←资源」的 join 命中，**已删除组的资源依旧对用户可见**。
   **修法**：`sqlite.pragma('foreign_keys = ON')`（每个连接独立，必须在建连接时设）。已由断言 T21/T22 覆盖（删组后关联表计数为 0）。

7. **前端 `can()` 在 `onMounted` 时必然是 false。**
   权限由 `/api/auth/me` 异步拉回，`usePermissions` 是全局单例但首屏不一定就绪 → 在 `onMounted` 里用 `can('user:view')` 判断是否加载用户清单，会永远走「不加载」分支。
   **修法**：改 `watch(() => can('user:view'), ...)` 驱动加载，并加 `immediate: true`（覆盖「权限已在别的页面加载完、切换到本页时不会再变化」的情况）；模板里补一个「权限校验中」态，避免闪一下「缺少权限」。

## 11. 邮件服务（M3，已完成）

### 11.1 组成
| 文件 | 职责 |
| --- | --- |
| `server/lib/mailer.js` | `sendMail` / `verifyConnection` / `loadMailConfig` / `validateMailConfig` |
| `server/routes/settings.js` | `POST /api/admin/settings/email/test` |
| `portal/.../SettingsView.vue` | 邮件 Tab 去掉占位标注，接真实保存与测试 |

新增依赖：`nodemailer`（仅此一个，无传递依赖膨胀）。

### 11.2 接口
```
POST /api/admin/settings/email/test
Body: { to: 'you@example.com', config?: {...} }
```
- `config` 不传 → 用库里已保存的配置；传了 → 用「库里配置 + 本次覆盖」试发，**改完没保存也能先验证**
- 密码留空时不覆盖库里已存密码（避免「测一下把密码测没了」）
- 返回 `{ ok, to, messageId, response }`

### 11.3 端口与加密映射
| encryption | 端口 | 行为 |
| --- | --- | --- |
| `ssl` | 465 | 直连 TLS（`secure: true`） |
| `starttls` | 587 | 明文起连后升级（`requireTLS`） |
| `none` | 25 | 不加密（`ignoreTLS`） |

端口没填时按加密方式给默认值；TLS 证书默认严格校验，内网自签用 `SMTP_TLS_REJECT_UNAUTHORIZED=false` 放行（默认不开）。

### 11.4 密码语义（修掉一个隐患）
原先 `password: ''` 会**删除**库里已存的 SMTP 密码 —— 意味着管理员在系统设置里只改个系统名，邮件密码就被清空了。现改为：

- 不传 / 空串 → 保持不动
- 非空字符串 → 重新加密落库
- 显式 `null` → 清除

前端 `emailPayload()` 同步剔除空密码。断言 T15/T16 覆盖（改完品牌密码仍在、仍能发信）。

### 11.5 错误映射
`EAUTH / ECONNECTION / ETIMEDOUT / ESOCKET / EENVELOPE / EDNS` 转成中文提示（如 ESOCKET 会提示「465 用 SSL、587 用 STARTTLS」）。配置类问题返回 **400**，SMTP 端问题返回 **502**，不让运维在一堆 500 里翻 SMTP 报错。

### 11.6 业务侧怎么用
```js
const { sendMail } = require('../lib/mailer');
await sendMail({ to, subject: '邀请你加入', text, html });
```
配置从 `system_settings.email` 读，业务代码不碰 SMTP 细节。等有了真实调用方（邀请 / 通知 / 密码重置）直接接即可，本次刻意不做，避免凭空造功能。

### 11.7 验证
`walkthrough/verify-email.cjs` **20/20**，其中 `walkthrough/smtp-stub.cjs` 是一个最小 SMTP 服务端（支持 AUTH PLAIN/LOGIN），用于**真发一封信**而不只是验证报错文案。

### 11.8 新增踩坑
8. **断言读 SMTP 报文要先解 MIME。** 中文主题 / 显示名在报文里是 `=?UTF-8?B?...?=`，长主题还会被折成多段编码词 —— 直接拿原文匹配中文会误判成「没发出去」。要先合并折行再 base64 解码。

## 13. 角色权限页信息架构改造（已完成）

### 13.1 问题
原布局是「左侧角色列表 + 右侧两列权限卡片」，每个权限项占两行（名称 + 权限码）。24 个权限位下：

- 页面总高 **1349px**，视口 900px 需要滚动 449px 才能看到「保存权限」
- 权限项纵向占 15 个行位，卡片高度参差（6 项那组明显比 4 项那组长），右侧留白与拥挤同时存在
- 没有搜索 / 折叠 / 组内全选，权限位再涨就只能靠滚

### 13.2 改成什么
**左角色列表（sticky）+ 右分组折叠列表**，权限区内部结构为：

```
工具条：标题 · 搜索权限 · 已选 N/24 · 全部收起
├─ 用户 user        0/6   全选
│    ☐ 用户查看  user:view   ☐ 用户创建  user:create   ☐ 用户编辑  user:edit
├─ 角色 role        0/4   全选
└─ …
底栏：共 24 个权限位 · 有未保存的修改        [还原] [保存权限]
```

- 权限项从「两行」压成 **单行 h-9（36px）**，权限码右对齐到各自格线
- 外层由双列卡片改为**单列分组**，组内 `grid-cols-1 md:grid-cols-2 xl:grid-cols-3`
- 新增：权限搜索（命中自动展开该组）、组内全选/取消、全部展开收起、`dirty` 未保存提示、还原按钮
- 新增角色列表搜索框；角色项补「N 项权限」计数（后端 `GET /roles` 加了一个子查询）
- 删除确认从原生 `confirm()` 换成 `AppModal`（与全站视觉一致，也是原遗留项之一）

**实测收益**：页面 1349px → **1132px**，滚动量 449px → **232px**，权限项占用行位 15 → 11。

### 13.3 可扩展性（这是改造的重点，不只是好看）
分组完全由后端 `permissions.module` 驱动，前端**没有任何模块枚举**：

- 新权限位 → 只往 `permissions` 表插一行，页面自动多出勾选项
- 新模块 → 自动成组；`MODULE_LABEL` 未登记时回退显示原始 module 名，`MODULE_ORDER` 未登记则排在已登记模块之后
- 权限数量增长靠 搜索 + 折叠 + 组内全选 + 全部收起 承接，不依赖一次性平铺

这条结论有专门用例守着（`verify-roles-extend.cjs`，8 项）：真实插入 `audit:view` / `audit:export` / `billing:manage` 两条新模块权限，断言新分组自动出现、可勾选、总数与分母同步增长，跑完自动清理。

### 13.4 顺带修掉的对比度问题（全站受益，不只是本页）
新布局大量使用「浅底 + 小字」，用 `contrast-audit.cjs` 采样后发现两个此前没暴露的问题：

1. **暗色下 primary 按钮白字不达标（3.76）**。根因是暗色 ramp 把 `brand-600` 统一提亮 14% 当按钮底。
   但各主题色原始亮度差异很大 —— 靛蓝/紫罗兰原色就有 5.7~6.3，青碧/松绿/赤橙只有 3.6~3.8，**固定比例的提亮/压暗无法覆盖两端**。
   改为 `darkenToContrast()` 按 WCAG 反解：已达标的保持起始色不动，不达标的压暗到刚好达标（浅色从黑化 0.1 起算以保持既有观感，深色从 0 起算以保留饱和度）。
   同时把 primary 按钮暗色下的 hover 从「切到更亮的 700 档」改成「保持同色整体压暗 10%」—— 否则 hover 会击穿白字对比度。
2. **`text-brand-600` 语义冲突**。600 档在暗色下已作按钮底（被压暗），再当文字色用就变成「暗底暗字」（3.4~3.7）。
   把 7 处 `text-brand-600` 文字场景统一改为 `text-brand-700`（实测浅色 6.66 / 深色 6.04，两端都达标），600 档从此专职做「控件实底」。
3. 新布局里权限码原本用 `text-ink-400`，浅色白底只有 **3.62**（不达标），改为 `ink-500`（浅色 5.07 / 深色 6.40）。

### 13.6 新增踩坑
9. **`locator.count()` 会把 `v-show` 隐藏的元素也算进去。** 折叠用的是 `display:none`，计数仍是 24，导致「折叠生效」这条断言假通过。判定可见性必须用 `:visible` 伪类。
10. **`section.last()` 不等于「你以为的那个分组」。** 分组顺序由 `MODULE_ORDER` 决定（system 排最后），断言写「最后一个组是资源组」直接错位。给 `section` 加 `data-module`、给角色项加 `data-role-id`，用数据属性定位而不是位置。
11. **用例之间会互相污染。** `verify-brand-e2e.cjs` 原本把期望品牌名写死成上一次跑完留下的值，串联执行时被 `wt-theme.cjs` 改过的品牌名带崩（单独跑却全绿）。改为「自读现状 → 写用例值 → 断言 → 还原」，与执行顺序解耦。
12. **`fullPage` 截图前要滚回顶部。** 点击按钮会让页面滚动，此时 fullPage 截图的 sticky 侧栏会被重复渲染，出现「上下重影」的假象。

### 14.2 关键修复手法

**原子性（#1）**：给 `db.js` 加 `tx(fn)`。pg 借独立 client 走 `BEGIN/COMMIT`；sqlite 侧要额外做串行化 —— better-sqlite3 是同步驱动但 `query` 对外是 async，事务里一旦 `await`，其他请求的语句就可能插进本事务，所以显式加了一把 `chain` 串行锁，保证任一时刻只有「一条语句」或「一整个事务」在跑。

**竞态（#2）**：`selectRole` / `selectGroup` 用自增序号，响应回来先比对 `seq !== detailSeq` 就丢弃。`save()` 里也先固化 `roleId`，保存期间若已切走就不再改 `snapshot`，避免状态错位。

**自我保护（#3/#4）**：停用/删除前先 `countAdmins()`，唯一超管拒绝操作；`id === req.portalUser.id` 拒绝停用自己。

**限流（#5）**：`app.use('/api', apiLimiter)` + `router.post('/login', loginLimiter, ...)`。验证方式取 `RateLimit-Limit` 响应头，**不要真去撞满 10 次** —— 那会把后续所有测试脚本锁 5 分钟。

### 14.4 本轮踩坑（承接 13.6，编号续）

13. **用例要跟着实现走。** 给请求加了 `?page=&pageSize=` 之后，`wt-theme.cjs` 里 `page.route('**/api/admin/users')` 不再匹配（glob 末尾精确匹配），错误态断言随之失效 —— 改成正则 `/\/api\/admin\/users(\?|$)/`。
14. **成功提示会污染「已删除」断言。** 新增了「已删除资源组「X」」的 toast，`afterDel.includes(NAME)` 因此恒为真。这类断言应改为查接口，或在提示文案里不带对象名。
15. **console 的 "Failed to load resource" 不带 URL。** 用它判断 HTTP 失败无法区分 favicon 404 与真 500，必须改用 `page.on('response')` 按 URL 过滤。
16. **监听要在设好 token 之后注册。** 登录页未登录时打 `/api/auth/me` 必然 401，算进来会淹没真实失败。
17. **不要为了验证限流而真的触发限流。** 登录限流是 5 分钟 10 次，一旦撞满，后续所有脚本的登录都会 429。

### 14.5 已知未修（有意保留）
