> 评估对象：`D:/workbuddy_workspaces/fit2cloud-admin-scaffold`（Vue 3 + Vite + Tailwind，Express + SQLite 全栈脚手架）
> 本次范围：**优先级①「列表 loading / error 防白屏」**铺开到所有取数列表页
> 验证方式：本地全栈实例（端口 3100）+ Playwright 无头走查 + 文本化诊断

## 1. 背景与优化目标

原脚手架所有取数列表页（首页资源网格、用户管理、角色权限）存在同一类隐患：

- 列表数据走 `onMounted` 内裸 `await api()`，**没有 try/catch**；请求一旦失败异常直接冒泡到渲染期，页面白屏、控制台报错、用户无感知。
- 无 loading 态，数据返回前表格/网格空白，体验像「卡死」。
- 部分页面（如首页）虽有 try/catch 但**静默吞错**，失败时当空态处理，属误导性 UX（以为是「没数据」而非「挂了」）。

**优化目标**：统一一套 `loading / error / data` 三态，从根消除白屏；失败时给明确错误文案 + 重试按钮；加载中给明确 loading 指示。

## 5. 走查发现的真 bug 与修复（核心价值）

**症状**：走查早期出现「API 返回 200 成功，但页面恒显『加载失败』」的反常现象。

**根因**：`useAsync` 最初 `return { data, loading, error, run }` 返回**普通对象**。Vue 模板**只自动解包 setup 顶层返回 / 顶层 reactive 里的 ref**；普通对象内嵌套的 ref **不会**解包。因此模板里 `v-if="usersReq.error"` 拿到的是 **ref 对象本身**（永远 truthy）→ 错误态永远显示、数据永远不显示。

**修复**：`return reactive({ data, loading, error, run });` —— 用 `reactive` 包裹返回值，使模板访问 `usersReq.error` / `usersReq.loading` 时拿到的是解包后的真实值。

**验证**：修复后 `npm run build` 通过，重跑走查（§4 三张正常态截图）+ `diag2.cjs` 文本诊断（`all-normal-state-clean: true`），确认三页均正确渲染真实数据、错误态不再误触发。

> 这个 bug 靠纯代码 review 极难发现（逻辑上 `error` 初始为 `null`，看代码会觉得「没报错不该显示」），是 UI 走查最直接的价值体现。

## 7. 结论

- **优先级①目标达成**：三处取数列表页（首页资源、用户、角色）已统一 `loading/error/data` 三态，从根消除白屏，失败时给出明确文案 + 重试，加载中有明确指示。
- **附带修复**：`useAsync` 嵌套 ref 不解包的隐蔽 bug（会导致错误态恒显），已通过 `reactive` 包裹根治。
- **构建 / 走查 / 文本诊断三方交叉验证一致**，无遗留阻断问题。
